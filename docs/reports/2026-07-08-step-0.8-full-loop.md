   - Old: `/Volumes/Sensidine/Praxis.build/signals/<ts>-<signal_id>.json` (does not exist on the remote n8n host — known defect in ISSUE_REGISTER)
   - New: `/tmp/praxis-signals/<ts>-<signal_id>.json` (same filename scheme, set in the `Validate Signal Payload` code node)
2. **Telegram credential bound**: `Orchastrator-Mine` (id `F9Q7ibTWgyAQpNAT`, telegramApi) bound by reference to all 3 Telegram nodes (`Telegram Notify Success` / `Rejected` / `Write Failed`). ChatId `6156528469` and message texts unchanged. (Approved substitution for the never-created "PRAXIS xarq5bot" credential.)
3. **Write node reimplemented as a Code node** (same name `Write Signal File`, `onError: continueErrorOutput` preserved). Two remote-host defects forced this:
   - `/tmp/praxis-signals/` did not exist and the readWriteFile node does not create directories (first live test failed: "The file or directory does not exist"). The Execute Command node is not available on this n8n instance ("Unrecognized node type: n8n-nodes-base.executeCommand"), so mkdir cannot be a separate node.
   - Even with the directory created, n8n's file-access restriction blocked readWriteFile from writing to `/tmp` ("The file ... is not writable").
   - The Code node now does `fs.mkdirSync('/tmp/praxis-signals', { recursive: true })` + `fs.writeFileSync(...)`; failures route to the error output → `Respond 500 Write Error` → `Telegram Notify Write Failed`.
4. **Error branch rewired**: the Write → Respond 500 connection was stored under a non-standard `"error"` connection type and never fired (first test returned an empty 200 on write failure). Rewired as main output index 1, which is what `continueErrorOutput` actually emits.
5. **IF node fixed**: `Is Payload Valid` boolean condition failed under strict type validation ("Wrong type: '' is a string but was expecting a boolean"). Set `typeValidation: loose` + `singleValue: true` on the boolean-true operator.

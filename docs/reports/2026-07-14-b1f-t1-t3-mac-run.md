## 5. Analysis — where the rejection can and cannot be

Eliminated by evidence:
- Payload schema (byte-verified against ValidateSignal in sha e4581f4a — every check passes on paper for the T1 payloads).
- Drop path (incoming-sweep vs direct root mv), content age (0 s vs 20 s), symbol (NQ vs MNQ), file corruption (rejected copies byte-identical).
- Mac-side daemons as the mover: sweep only promotes; backlog/stale checks only alert. Only the VM consumer knows `rejected/`.
- Order-submission failure path: that path journals ACCEPTED before moving to rejected/; journal has zero lines.

Therefore every file was rejected **pre-dedup** — in `ProcessFile` at the read, parse, or validate stage. Leading hypothesis: **VM-side `File.ReadAllText` over the Parallels share returns empty/partial content (→ "malformed JSON") or throws IOException repeatedly (5 rapid FSW events can burn `MaxReadAttempts=5` → "unreadable after 5 attempts")**, rejecting every file regardless of content. Caveat on T3: under this hypothesis T3's PASS is vacuous (any file would reject); T3 is only confirmed non-vacuous once a valid file is ACCEPTED.

The discriminating fact — the verbatim `PRAXIS-B1f … REJECTED (file '…') — reason` lines — exists only in NT8 Output/Log/trace inside the VM.

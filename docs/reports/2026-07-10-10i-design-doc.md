## Key design choices
- **Boundary crossing = data, not execution.** n8n (Docker) Telegram Trigger writes a
  JSON command file into the existing host-mounted `local-files` dir
  (`tg-inbox/`); a host launchd agent (WatchPaths + 60s poll) runs a runner script
  that invokes `claude -p` in read/report mode and replies via the existing
  notify.sh → n8n → Telegram path. Direct reuse of the proven B1-c / B1-b-fu pattern.
- **TCC constraint designed in:** repo scripts are SOURCE only; installer copies to
  `~/Library/Application Support/Praxis/bin/`; plist points internal; data/logs under
  `/Users/admin/praxis-tg/`. Cites the B1-c "Operation not permitted" incident.
- **Command-file spec:** `{update_id, chat_id, from_id, text, ts}`; dedupe on
  update_id; staleness window; atomic `.tmp`→rename writes; malformed → `failed/`.
- **Security (10 numbered controls):** double sender allowlist (n8n + host), text as
  data never shell (argv/file only), enumerated verb whitelist, flock single-flight +
  rate limit, least-privilege read-only claude profile per skill section G, append-
  only audit log outside the repo, two-layer kill switch (DISABLED flag / plist),
  replies always state what ran, no secrets in channel.
- **Failure modes covered:** WatchPaths ~10s throttle (bead 8xf; drain-queue-per-wake
  mitigation), duplicate deliveries, crash-stranded files (sweep/requeue), claude CLI
  dead (error reply), n8n container down (both directions die together — unambiguous
  symptom; heartbeat-style liveness extension noted), sleep backlog (staleness
  rejection), account compromise, group-chat/forwarding, malformed files.
